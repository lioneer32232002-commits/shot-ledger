# SPEC_M13：生涯數字改算「進球、不含上籃」＋徽章家族重整

> 使用者回饋（2026-07-28）：
> 1.「生涯累計那邊有計算上籃嗎？我覺得計算上籃的有點作弊，因為上籃一定命中率會高。」
> 2.「累積顆數我現在才發現是總投，不是總進，可以改成總進比較有意思。」
> 3.「3 分球應該也要另外開徽章。」
>
> 定案方向：**生涯這一層全部改用「不含上籃的數字」**，投量徽章換成進球徽章，
> 另開三分家族。單場／期間統計不動。

---

## 0. 為什麼上籃要排除

上籃的命中率天生就比其他球種高——階梯本身就承認這件事：第 12 關 `lin_taiwan`
的過關門檻是**上籃 ≥70%**，而其餘所有球種的門檻都落在 30〜55%。既然如此，
把上籃算進生涯命中率與累計數，等於留一條「一直投上籃就能刷高數字」的後門。

排除範圍**只到「生涯」這一層**：

| 算不算上籃 | 對象 |
|---|---|
| ❌ 不算 | 生涯累計卡（統計頁）、練球頁累計行、設定頁資料狀態、生涯分享卡、進球徽章 |
| ✅ 照算 | 單場統計、命中率趨勢、熱力格日曆、期間熱區、週目標、挑戰過關／三星判定 |

理由：後者回答的是「這段時間練了什麼」，上籃本來就是練習的一部分，
而且 `lin_taiwan` 的 passRule 直接考上籃——那條路徑一動就是改關卡難度，不在本次範圍。

實作：`stats.js` 的 `LIFETIME_EXCLUDED_TYPES = ['layup']` ＋ `countsForLifetime(round)`，
`lifetimeTotals()` 是唯一的守門員，其餘顯示端都經過它，不各自過濾。

## 1. 投量徽章 → 進球徽章

`volume_*`（總**出手**、含上籃）整個家族換成 `makes_*`（總**進球**、不含上籃）。

### 1.1 門檻換算基準（不是憑感覺配的）

| 項目 | 數字 |
|---|---|
| 15 關完整版各打一輪 | 181 輪＝1,810 球出手 |
| 其中上籃輪 | 11 輪＝110 球（不列入） |
| 不含上籃的出手 | **1,700 球** |
| 以各關過關門檻推估的進球（2 分 50%／3 分 40%／深 3 32%／罰球 78%） | **約 870 進** |
| 一份完整菜單 | 約 12 輪＝120 球 ≈ 60 進 |

| id | 門檻 | 約當 |
|---|---|---|
| `makes_500` | 500 進 | 約 8 場（起步就摸得到） |
| `makes_1000` | 1,000 進 | 階梯全破 1 趟多 |
| `makes_2000` | 2,000 進 | 階梯全破 2.3 趟 |
| `makes_3500` | 3,500 進 | 階梯全破 4 趟 |
| `makes_5000` | 5,000 進 | 階梯全破 5.7 趟 |
| `makes_8000` | 8,000 進 | 階梯全破 9 趟 ≈ 130 場，約兩年的長期目標 |

前三階好拿、後面拉開：舊制頂階 50,000 出手（≈400 場）遭不到，
等差的 500〜3,000 又半年就收集完，這組是兩者之間。

### 1.2 三分家族（新增）

同一趟全階梯的三分進球約佔總進球的 32%（282／871），門檻照這個比例配 4 階：

| id | 門檻 |
|---|---|
| `threes_200` | 200 進 |
| `threes_500` | 500 進 |
| `threes_1000` | 1,000 進 |
| `threes_2000` | 2,000 進 |

**深三算三分**（`THREE_TYPES = ['3pt', 'deep3']`）——深三就是站得更遠的三分球。
注意這只是徽章／生涯口徑，統計頁的球種篩選仍把 3 分與深 3 分開列。

### 1.3 徽章總數 17 → 21

出席 5／進球 6／三分 4／摘星 3／階梯 3。

⚠️ **21 是生涯分享卡的硬上限**：`sharecard.js layoutBadgeRows()` 最多三列 ×
每列 7 顆＝21 格，第 22 顆起最後一格會變成「＋N」收尾。再開新家族之前要先
處理那邊的版面。徽章牆（統計頁）是 3 欄 grid，不受影響。

## 2. 數字盤（SPEC_M12 的延伸，不改設計語言）

| 家族 | 數字盤內容 | 單位 | 家族標記 |
|---|---|---|---|
| 進球 `makes` | `500` `1K` `2K` `3.5K` `5K` `8K` | `進` | `ball`（籃球） |
| 三分 `threes` | `200` `500` `1K` `2K` | `進` | `arc`（**新增**：三分線） |

- **未滿千寫原數字**：`formatMakesTarget()` 對 <1000 直接輸出數字，不寫成 `0.5K`。
- **進球家族補上單位「進」**：SPEC_M12 時代投量是「無單位（K 已表意）」，
  但這次改版的重點就是「投了幾顆 vs 進了幾顆」的差別，分享卡上沒有文字說明，
  單位必須自己把話講完。牆與成就條旁邊本來就有徽章全名，維持 `showUnit=false`。
- **兩個家族同樣掛「進」**，靠正下方的家族標記區分（籃球 vs 三分線）。
- `arc` 圖示＝底線＋兩側直線段＋圓弧＋中央小圓（籃框），就是球場圖上半場三分線的
  形狀，縮到 14px 仍是好認的「ㄩ」形輪廓，不會跟 `ball` 撞。
  ⚠️ 圖示只能用 `<path>` 與 `<circle>`：`sharecard.js drawBadgeIconShape()` 只解析
  這兩種元素，用 `rect`／`line`／`polyline` 會被靜靜略過。

### 2.1 分享卡字級量測要含單位

`computeBadgeNumFontSize()` 原本只量數字（最寬 `2.5K`、比例 0.58）。進球家族掛上
「進」之後最寬的一列變成 `3.5K進`，只量數字會讓單位戳出圓盤外圈。改為
**數字（800 字重）＋單位（700 字重、`BADGE_UNIT_RATIO` 0.55）一起量**，比例
放到 0.72（＝原數字寬度再加一個 CJK 單位字）。

實測 112px 圓盤：字級 29 → 28（視覺等同），`3.5K進` 總寬 78px＝直徑的 69%，
最小圓盤 76px 時字級 19。量測與繪製共用同一個 `BADGE_UNIT_RATIO`，不能各拿一個數字。

## 3. Migration（schema 12 → 13）

```
1. 移除所有 volume_* 徽章
2. 依 lifetimeMakes(sessions)      發 makes_*
3. 依 lifetimeThreeMakes(sessions) 發 threes_*
```

**這是全 App 唯一一次「減徽章」**，其餘所有 migration 都是只加不減。理由：

- 舊 `volume_*` 的門檻與新制不同義（1,000 出手 ≠ 1,000 進球），留著會讓徽章牆
  同時掛著兩套互相矛盾的累計數；
- 新舊都是純累計、單調成長，重算不會讓任何「真的投進去的球」消失，
  只是換一把尺重量一次。

出席／摘星／階梯三個家族完全不動。另外 `schema < 11` 那段回溯發章原本也會補發
`volume_*`，已拿掉——發了也會被 v13 移掉。
