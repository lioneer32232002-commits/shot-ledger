# SPEC_M14 — 「留下來」包（2026-07-30）

> 這一包刻意**不加大功能**。`docs/COMPETITORS.md` §5.5 的結論是「最大風險不是功能
> 不夠，是根本沒人在找這類產品」，所以重心放在留存動力與分發前的體質：
> 補會讓人流失的洞（沒有次級目標、資料可能被清掉、球場訊號差時開不起來），
> 不是再堆一層新玩法。

## 0. 先做的稽核（不用 iOS 裝置也能做的部分）

使用者沒有 iOS 裝置，`§4` 的動機（Safari 對 script-writable storage 的 7 天上限）
無法直接實測——**這件事本質上也不可能實測**（要等 7 天且期間完全不互動）。
因此 §4 的設計原則是：**不靠偵測、不靠平台判斷**，只做「無論哪個瀏覽器都對」的事。

順手做完的靜態稽核（2026-07-30）：

| 項目 | 結果 |
|---|---|
| `100vh` 在 iOS 動態工具列下的高度跳動 | ✅ 全站用 `100dvh`（`app.css` 6 處） |
| 安全區（劉海／home bar） | ✅ `viewport-fit=cover` ＋ `env(safe-area-inset-*)`（`tokens.css:82`） |
| Safari 嚴格日期解析（`'YYYY-MM-DD HH:mm'` → Invalid Date） | ✅ 全站 `new Date()` 的輸入都是 `toISOString()` 產生的 ISO 字串 |
| 分享卡 canvas 尺寸 | ✅ 1080×1350 ＝ 1.46 M px，遠低於 iOS 的 canvas 面積上限 |
| `navigator.storage.persist()` | ⚠️ Safari 未實作 → iOS 上 `storagePersisted` 永遠是 null，設定頁那行提示不會出現。這正是 §4 要靠「加到主畫面」而不是靠 `persist()` 的原因 |

## 1. 連莊（連續達標輪）

### 1.1 根因

`session.js` 的 `forecast-banner`（不可達標橫幅）誠實地告訴使用者「這次挑戰已無法
達標」，然後給兩個選項：繼續投完、或提前結束。問題是**繼續投完沒有任何目標**——
該節剩下的輪次不再影響任何顯示中的數字。挑戰場次多數是沒過關的，所以「下半場沒
有目標」其實是常態，這是耐玩度最大的洞。

`COMPETITORS.md` §5.2 已點名 streaks 是手動型工具唯一被明確抱怨的統計缺口。但
**「連續進球」在快速模式下算不出來**（沒有 `seq`，只有每輪進幾顆），而使用者實際
上不用逐球模式（SPEC_M10 已據此把疲勞趨勢改成單場逐輪）。所以這裡做的是它的
正確在地版本：**以「輪」為單位的連莊**，快速模式零額外輸入成本。

### 1.2 定義

**一輪達到該球種的連莊門檻 → 算一輪達標；連續達標的輪次長度＝連莊數。**

門檻按球種難度分級（每 10 球要進幾顆），實投數不是 10 時等比換算（`Math.ceil`）：

| 球種 | 罰球 | 上籃 | 2 分 | 3 分 | 深 3 |
|---|---|---|---|---|---|
| 每 10 球需進 | 8 | 8 | 6 | 5 | 4 |

- **為什麼要分級**：固定 6/10 的話，深三輪永遠達不到——而使用者正好卡在深三關卡，
  功能會剛好死在最需要它的地方。分級後每種球都「難但做得到」。
- **為什麼略高於過關門檻**（例：2 分門檻 45〜55%，連莊要 60%）：連莊是**加分目標**
  不是關卡門檻，它要在挑戰已無望時還值得追，就必須自己夠硬。
- `attempts <= 0` 的輪視為中斷（實務上不存在，實投數 stepper 只給 1〜20，純防禦）。
- 連莊不跨節累計：一節就是一段，跨日「連續練習天數」是另一個既有系統（出席徽章）。

### 1.3 顯示

- **練習中**（`renderActive`）：輸入區上方一條 streak rail——目前連莊數 ＋
  「本輪 ≥N 顆續莊／開莊」。這是唯一一個在挑戰已無望時還會動的數字。
- **結算頁**：本節最長連莊 ＋ 生涯最佳（生涯最佳現算，不進 progress，不需 schema）。
- 這一包**不發徽章**。理由：徽章家族剛在 M13／M12 重整過（21 顆、分享卡三列 7+7+7
  的版面上限），加家族要連動 `sharecard.layoutBadgeRows` 與 `check_ladder`；先讓
  連莊在實地跑一陣子、確認門檻對不對，再決定要不要發章。

### 1.4 實作

`js/stats.js` 新增純函式（純函式層鐵律：不碰 DOM／localStorage）：

```
STREAK_BAR_PER_10   球種 → 每 10 球門檻（export，UI 要顯示門檻表）
roundBar(round)      該輪需要幾顆（等比換算），attempts<=0 回 null
isStreakRound(round) 該輪是否達標
roundStreak(rounds)  { best, current, bestEnd }
bestRoundStreakAllTime(sessions, excludeSessionId)
```

`tools/test_stats.mjs` 同步補測（部署鐵律 1）。

## 2. 結算頁重排 ＋ 射手小語

### 2.1 根因

`renderSessionSummary` 現行順序是：總計 → 球種 → 輪次曲線 → 前後段 → 熱區 →
**挑戰結果** → 等級對照 → 備份 → 動作。挑戰場次最想看的星星與過關判定排在第 6 段，
手機上要捲過三張圖表才看得到。

### 2.2 新順序

```
header → 總計 → [挑戰結果] → [連莊] → 球種 → 熱區
       → <details 輪次曲線> → <details 前後段> → [射手小語]
       → [等級對照] → [加到主畫面 | 備份提醒] → 動作
```

- 挑戰結果提到總計之後（非挑戰場次此段本來就不存在，順序自然不變）。
- 輪次曲線與前後段收進 `<details>`（預設收合）：它們是「回頭分析」用的，不是
  剛投完最想看的。`court.js` 用固定 viewBox、不量測 DOM，收在 `<details>` 裡展開
  後不會壞版（熱區圖本身仍維持展開，那是招牌視覺）。
- `<details>` 的 summary 要自己畫箭頭：預設 marker 在各家瀏覽器長得不一樣。

### 2.3 射手小語

素材已經寫好了，只是從來沒被重看過——`menus.js` 每關都有 `career.fact`（一句事蹟，
雙來源查證）與 `basis`（訓練依據＋出處連結），現在只活在「變體選擇面板」裡，開始
挑戰前看一次就再也不出現。挑戰場次結算時把它接進行為迴圈：一句該關球員的事實
＋出處連結。

紀律不變：維持「依公開報導風格改編・非本人菜單」的標註立場，不得寫成
「這是 XXX 的訓練菜單」。

## 3. 啟動效能

### 3.1 SW 策略：全站 network-first → 靜態資源 cache-first

`sw.js` 現行是全站 network-first，只有 `fetch` **失敗**才吃快取。球場的弱訊號情境
不是「失敗」而是「很慢」——瀏覽器會一直等，快取形同不存在。`PLAN.md` §6 的
「開 App 到可投球 ≤3 點擊」管了點擊數，沒管到「開 App 到畫面出現」。

新策略：
- **導覽請求／HTML（殼）**：network-first，但加 **2.5 秒 race timeout**，逾時就用
  快取先把畫面畫出來（避免舊版黏住小站的原始考量仍成立）。
- **其餘同源 GET（js／css／圖）**：cache-first ＋ 背景 revalidate。安全性由既有的
  部署鐵律保證——每次改版都遞增 `CACHE_NAME`，`activate` 會刪掉舊版快取，所以
  新版 SW 生效後第一次請求一定回源。

### 3.2 首訪不要背景吃掉 2 MB

`CORE` 現在把 5 張分享卡底圖（約 810 KB）＋3 張首頁大圖（約 587 KB）全列進去，
install 階段一次抓完。分享卡底圖只有按下「分享成績卡」才用得到。

- cardbg 移出 `CORE`，改成第一次開分享面板時由頁面 `postMessage({type:'precache-cardbg'})`
  請 SW 補快取（頁面不自己開 cache：`CACHE_NAME` 只該有一個真實來源）。
- 首頁三張大圖留在 `CORE`：它是新訪客的落地頁，離線可用有意義。

### 3.3 分享卡引擎改動態載入

`js/sharecard.js` 是最大的檔（75 KB），只在按下分享時需要，但 `session.js` 與
`statspage.js` 都靜態 import 它 → 首屏就得下載＋解析。改成 `await import()`。
SW 的 `CORE` 仍保留它（離線也要能分享），這裡省的是**首屏關鍵路徑**。

`js/statspage.js`（27 KB）暫不動：要改成動態載入得把 `app.js` 的 router 變成
async，風險與收益不成比例，留待日後真有需要再說。

## 4. 資料保命

### 4.1 根因

Safari 對「沒有加到主畫面」的網站有 script-writable storage 的 7 天上限——使用者
兩週沒開就可能整份 localStorage 被清掉；**已安裝的 PWA 不受此限**。而
`navigator.storage.persist()` Safari 沒實作，那條路在 iOS 上是空的。

現行備份提醒門檻是「未備份節數 ≥ 30」（`session.js:1506`）。對「練了 5 次、隔兩週
回來發現全空」這個情境完全來不及——那是最容易永久流失的使用者。

### 4.2 做法

**(a) 備份提醒改「節數 或 天數」二者取先到**（`store.backupNudge()`）：

- 已結束且未備份的節數 `count < 3` → 一律不打擾（剛開始用的人不該被嚇）。
- `count >= 30`（原規則，維持）→ 提醒，文案講節數。
- 距上次備份 ≥ 14 天（從未備份過則從最早一節算）→ 提醒，文案講天數。
- 「先不用」的 snooze 兩條各自獨立：節數要再多 30 次，天數要再過 14 天。

**(b) 加到主畫面引導**：非 standalone、已完成 ≥ 2 節、未按過「不用了」時，在結算頁
出一張卡，理由直接講白——不是為了方便，是為了紀錄不被瀏覽器清掉。同一頁不與
備份提醒並存（A2HS 優先，備份提醒讓位）。

平台文案分兩種（iOS 只能手動加、Android/桌面 Chrome 系有 `beforeinstallprompt`）：
偵測只用來**決定講哪句話**，不用來決定要不要顯示——判斷錯了最壞情況是文案不精確，
不會有人看不到卡片。新增 `js/env.js` 放這幾個環境判斷（`isStandalone` / `isIOS`）。

**(c) 設定頁**：「上次備份」補上「N 天前」；非 standalone 時多一行說明為什麼建議
加到主畫面。

### 4.3 schema 14

新增兩個 settings 欄位（migration 只加不減）：

- `a2hsDismissed: boolean` — 使用者按過「不用了」
- `backupNudgeSnoozedAt: string|null` — 天數規則的 snooze 基準時間
