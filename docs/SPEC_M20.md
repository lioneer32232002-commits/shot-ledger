# SPEC_M20 — 上籃獨立門牌 ＋ 鬼影對照（2026-07-30）

> 兩件都是之前列在待辦、使用者同意要做的。

## 1. 上籃獨立門牌

### 1.1 為什麼要做

M13 把上籃排除在生涯數字與進球徽章之外，**那個決定是對的**：上籃命中率天生偏高
（第 13 關的門檻就是上籃 ≥70%，其餘球種都在 30〜55%），混進去等於「一直投上籃」
就能同時灌水命中率與徽章進度。

但副作用是：菜單裡有 **11 輪上籃**（第 1／2／3／12／13 關），投了卻在任何地方都
看不到——使用者會覺得白投。

### 1.2 為什麼獨立家族不會重現 M13 的問題

M13 的問題是「**同一個**命中率／計數器被上籃拉高」。獨立計數、獨立門檻就沒有這件事，
跟三分家族一樣是平行的一條線（三分同樣可以在自由練習裡刷，那從來不是問題）。

### 1.3 內容

- **獨立累計**：`stats.lifetimeLayupTotals()`。顯示在
  - 統計頁生涯累計卡：底部一條細線隔開的「上籃另計 N 投 / M 進（X%）」
    （**必須跟上面那組數字分開**，排在一起會被誤讀成「總投裡面有含」）；
  - 設定頁「資料狀態」同一行格式。
  - 兩處都在 `att === 0` 時整行不顯示（沒投過上籃的人不用看到這個概念）。
- **獨立徽章家族**：`layups_100 / 300 / 800`，新圖示 `rim`（籃框橫線＋四條網線＋
  框正上方的球，與三分的「ㄩ」形 `arc` 明顯不同）。
  門檻依量體推算：有上籃的 5 關各打一次＝11 輪 110 球約 80 進，
  100 進 ≈ 那 5 關跑 1.2 趟、800 進 ≈ 10 趟，節奏與其他家族對得上。
- **schema 16 回溯發章**：上籃一直都記在 rounds 裡，只是沒人替它計數；新家族上線時
  要把過去投進的補算回來，否則老使用者會看到一個從 0 開始的家族。只加不減。

### 1.4 已知取捨：生涯分享卡的 21 格上限（**已於 SPEC_M21 解決**）

> 2026-07-30 後續：使用者要求「讓 24 顆全滿」，已實作——見 `docs/SPEC_M21.md`。
> 以下保留當時的分析紀錄。

`sharecard.layoutBadgeRows` 一次只畫得下 **21 顆**（三列 ×7，超過就把最後一格換成
「＋N」）。加了上籃家族後定義總數是 **24**，所以「已獲得 22 顆以上」的人卡片上會出現
＋N。那是既有的溢出設計、不是壞掉（已實測 23 顆仍正常產出 1080×1350）。

要真的畫滿 24 顆有兩條路，兩條都會動到已經調好的版面，**留待日後真有需要再處理**：
1. 一列 8 顆：圓盤要從 112px 縮到 95px（全體使用者的卡片外觀都會變）。
2. 加第四列：吃掉固定卡高（1350px）的垂直空間，其他段落的間隙分配要重算。

## 2. 鬼影對照

### 2.1 問題

練習中比得到門檻（`renderPassRuleBars`），比不到自己。「我今天到底有沒有比上次好」
要等結算頁的個人最佳才知道——那時候已經投完了，沒得調整。

### 2.2 做法

- `stats.bestSessionFor(sessions, menuId, variant, excludeId)`：同菜單同變體、已結束、
  整節命中率最高的那一場當「鬼影」。（`progress.best` 只存 `{pct, att, mk, date}`
  沒有逐輪資料，所以要回頭從 sessions 找那一節。）
- `stats.ghostAt(currentRounds, ghostRounds)`：兩節在「第 k 輪為止」的**累計**命中率，
  k = 兩者輪數的較小值。
  **為什麼比累計而不是比單輪**：10 球一輪差一顆就是 10 個百分點，單輪跳動太大讀不出
  訊息；累計才回答進行中真正想知道的問題——「照這個節奏，我會不會贏過自己最好的
  那一場」。
- 顯示：挑戰進度條下方一條虛線框的 rail——「個人最佳同期（第 3 輪為止）／
  你 67%　最佳當時 50%／**+17**」。差距用**顏色＋正負號雙重編碼**（色盲使用者只看
  符號也讀得出領先或落後），並附 `aria-label` 講完整句子。
- 第一次打這關（沒有可比場次）→ 整塊不顯示，不用空狀態佔位。
- 視覺上刻意比連莊 rail 安靜：連莊是「正在發生的事」（會跳、會斷），鬼影是背景參照，
  不該跟挑戰進度條搶注意力。

⚠️ **本機驗證再次踩到 SW**（第四次，寫在這裡當提醒）：SW 是 cache-first，而它 install
階段的 `cache.addAll()` 也會吃瀏覽器的 HTTP 快取，所以「unregister → 刪 caches →
reload」有時仍會拿到舊模組（頁面一載入就重新註冊、立刻 claim，連 `fetch(cache:'reload')`
都會被它攔）。**要驗顯示層最可靠的方式是用帶 query 的動態 import 取得乾淨模組實例，
再把 HTML 渲染進 detached div 檢查**——本次的徽章牆與分享卡就是這樣驗的。
